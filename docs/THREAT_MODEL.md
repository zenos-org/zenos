# ZENOS threat model (Developer Preview)

This document says what ZENOS is meant to protect, against whom, and — most importantly for a preview — which
protections are real today and which are only demonstrated. It is updated with every release.

## Assets

1. The contents of classified files (levels L1–L5).
2. The keys that decrypt them.
3. The audit trail: who opened, moved or sent what, on which device, when.
4. Availability: files must survive the loss of a building or a node.

## Adversaries considered

- **A careless or coerced insider** who copies files to USB, uploads them, or opens many files at once.
- **A targeted employee** pressured by a foreign service: ZENOS aims to make "the person with access" a poor
  target, because access is per request, recorded, and multi-person approved.
- **Malware on an endpoint** that tries to exfiltrate data or rewrite its own audit trail.
- **A compromised storage node or relay** (sees only ciphertext and fragments).

Out of scope for now: physical attacks on running hardware, hardware implants, and side channels.

## Trust boundaries (target design)

```
user session  ──(cannot touch)──▶  root services: sentinel, firewall, ledger, key agent
key agent     ──(keys never leave)─▶  TPM / FIDO2 device
approvals     ──(signed on)──────▶  each approver's own device
audit log     ──(shipped to)─────▶  consortium nodes outside the endpoint
```

## What is real today and what is not

| Protection | Today | Gap to close |
|---|---|---|
| File sealing (AES-256-GCM, fragmented, signed header) | Real cryptography. Installed system: the level keys, fragment keys and the signing key belong to root (`zenos-keyd`, `/var/lib/zenos/keys`); every seal and unseal goes through it. It hands out plaintext only up to the user's clearance (set by the administrator in `/etc/zenos/clearance`) or for one exact file with a grant the officers signed (verified against the enrolled keys), and records every unseal and refusal in the root ledger, which is shipped off the PC. Tested: the user cannot read the key files; an L4 file is refused at clearance L2; an officer-approved grant (signed in the officer's browser) opens exactly that file. | The keys are root-owned files, not yet in a TPM; root on the PC can read them. On a stolen, switched-off PC they are protected by the installer's full-disk encryption (checked by default, passphrase at boot), not by hardware. Keys are per PC, so a sealed file opens only on the PC that sealed it (no shared key service yet). Files sealed before the agent was installed (user-held keys) no longer verify. In the development layout keys are still in the user's home. |
| Plaintext only in RAM while open | Implemented for viewers and for the ZENOS office apps (a sealed .docx/.xlsx/.pptx is edited from a RAM copy, saved back only to it and sealed again; web storage is ephemeral) | Applications could still write copies; needs mandatory access control (SELinux MLS). |
| Copy and screen capture of L3+ | Sealed files of L3 and above: nothing can be copied out of the office apps (copy, cut, drag and the clipboard API are refused; pasting in works). Installed system: while any L3+ sealed file is on the user's screen, the guard refuses screen-capture programs (Spectacle, scrot, flameshot, OBS, …). Tested: scrot works with nothing or an L2 file open, is refused with an L4 file open, works again after it closes; Ctrl+C in an L4 sheet leaves the clipboard unchanged. Copy and paste between sealed windows works through a level clipboard in the key agent (RAM only, 30 minutes): an L4 copy pastes into L4 and higher windows, never into lower ones or into other programs, and every copy is logged with its level and length (tested: L4 to L4 works, L4 to L3 pastes the ordinary clipboard instead, the X11 clipboard stays untouched, a later copy in an ordinary program takes over). Selected text in an L3+ window is emptied out of the X11 PRIMARY selection at once, so a middle click elsewhere pastes nothing (tested: an L4 window leaves PRIMARY empty, an L2 window keeps it). Sealed L3+ text opens in a viewer without selection, copy or drag (tested: clipboard and the X11 primary selection unchanged). The image, video and PDF apps refuse copy, drag and the right-click menu for L3+ (tested in the PDF app: Ctrl+A, Ctrl+C on an L4 PDF left the clipboard unchanged). | The level clipboard lives in the key agent's memory for the user's account; another program running as the same user could ask the agent for it. A program the guard does not know, a camera pointed at the screen, or a user-written X11 capture script are not stopped. |
| Printing sealed files | The office apps put a red banner with the level, file name, user and time on every printed page of a sealed file. Files above `print_max_level` (default 3, `/etc/zenos/policy.conf`) cannot be printed from the PC; every print and refused print is written to the audit log. Tested: window.print() in an L4 sealed window shows the refusal and nothing is printed. | A photo of the screen, or printing from a program outside the office apps, is not covered. The banner is a deterrent and a trace, not a protection. |
| Approval-based access | Implemented, signatures verified against officer public keys installed by the administrator (`/etc/zenos/approvers`, root-owned). Release of a stopped PC, access requests (opening above your level) and pre-filed operations are all signed on the officers' own devices; once officers are enrolled, only their enrolled keys count (a key the user makes up is ignored — tested). ZENOS Messages makes an Ed25519 key in the officer's browser (WebCrypto, non-extractable, kept in IndexedDB); the administrator enrolls its public key with `zenos_guardd.py --enroll NAME KEY`. The request reaches the officer end-to-end encrypted, the officer's device recomputes the digest from what it shows and signs it, and the guard verifies the signature against the enrolled key and its own copy of the request. The match code is never sent; the officer reads it off the stopped screen. Tested end to end (wrong code refused, decline renews the request, an old key is refused, three signatures release). | The demo approval page (keys on the same machine) still exists for development without enrolled officers; the browser key is software-backed (not yet a FIDO2/secure-element key); an officer who loses the device must be re-enrolled. |
| Anomaly stop | Installed system: `zenos-guardd` runs as root, sees every open of a protected file and every write to the exit with the process id (fanotify), keeps the stop state, release requests and quarantine root-owned, freezes every process of the user (anything new is frozen within a second) and shows the stop notice as root. Release needs the required number of valid officer signatures. Tested end to end: the user cannot write the stop state; a forged signature is refused; three valid signatures release the PC and cancel the operation. | Moves into the exit are seen by inotify (no process id). The display server, the window manager and the messenger keep running during a stop. The development layout (`~/.local/share/zenos`) still uses the old user-level watcher. |
| Network sentinel / firewall | Root service with an eBPF (bpftrace) sensor and iptables chains | Not reviewed; outbound policy is per incident. |
| Tamper-evident ledger | Hash chain + Merkle anchors, verified to detect a self-consistent local rewrite. Installed system: `zenos-auditship` sends the guard's ledger and every user's ledger to one or more audit nodes (`zenos_auditnode.py`, run on a machine the PC users do not control) every 30 seconds, in batches signed with the PC's root-only audit key. A node accepts only records that continue the chain it holds; a changed past record, a gap, a broken link or a bad signature is refused and alerted, and every accepted batch gets a receipt signed by the node. Tested: unit test (a PC rebuilds a valid local chain without the "halt" record; the node keeps the original and raises "history-rewritten") and end to end on the test system. | A record can still be changed in the seconds before it is shipped, and a PC kept offline ships nothing (the node reports it as silent after 90 seconds, but cannot see what happened meanwhile). User ledgers are writable by that user. The node's alerts are a file, not yet a dashboard or a notification. Audit nodes of different parties compare their copies and report forks with both signed statements; the history the consortium stands behind is the longest prefix a majority of them hold identically (`--consortium-status`). This assumes most parties are honest, and records past that prefix are not settled until a majority holds them. |
| Distributed storage | Each sealed file is encrypted again with its own key, erasure-coded 3-of-5 and spread over storage nodes on the network (Hyperswarm, Noise-encrypted connections, the grid's own bootstrap). Nodes and PCs are certified by the grid administrator (Ed25519; role, highest level, zone, bound to the key the connection proves). A node answers nothing to an uncertified peer, serves a file only up to the requester's clearance, never takes a level above its own clearance and checks every shard's hash on arrival. At most n-k shards per zone, so losing a whole site loses no file. Lost shards are rebuilt from ciphertext, without the key. Tested in CI (a certified grid on one machine) and on two machines (packaged services). | Certificates expire (one year by default) and keys can be revoked with an administrator-signed list that spreads from peer to peer and is checked on every request; a revoked peer keeps its access only until the list reaches the nodes it talks to. The administrator key is a file, not a hardware token. A certified PC can read the ciphertext shards of any file at or below its clearance (it still needs the file's capability to decrypt). The capability is kept in the PC's index sealed at the file's level, not issued through the approval flow. Nodes do not limit how often a certified peer asks. |
| Terminal disabled | Hidden from the UI. Installed system: `zenos-guardd` answers every start of a terminal program (konsole, xterm, gnome-terminal, kitty, …; fanotify exec permission) and refuses it for the desktop user; root and other accounts are allowed. Tested: the user gets "Operation not permitted", root starts it, other programs are unaffected. Policy `terminal = allowed` in `/etc/zenos/policy.conf` turns it off. KRunner's command line (Alt+Space) is turned off with KDE's Kiosk restriction `shell_access=false`, locked with `[$i]` in `/etc/xdg/kdeglobals`. Tested in the live image: before, KRunner offered "Run" for a typed command and ran it; after, it offers nothing and nothing runs. | Raises the bar only: a copied terminal binary or an interpreter (python3) still give a shell. Closing that needs `noexec` home/tmp mounts and SELinux confinement of the user. |
| Messenger E2E | libsignal (Signal protocol). Accounts are bound to the device that registered them: every request made for an account (key updates, channel membership, approvals, lookups, call tokens, the account's own number) is signed with its identity key; unsigned, foreign-key and replayed requests are refused and audited. A new device takes an account over only by verifying the number already registered to it. Relay administration (call servers, channel seeding) needs a token kept on the relay's host. Tested: `tests/messenger_binding.js`, plus takeover attempts against a running relay. | With `ZENOS_RELAY_ENROLL=1` a new account needs a one-time code the administrator issued for that name on the relay host (`POST /enroll`); without it (the default for test relays) whoever registers a name first owns it. Losing both the device and the number means an administrator must reset the account. Test deployments used a Cloudflare quick tunnel, which is for testing only. |
| Level-gated AI | Two layers. The launcher and the office apps offer only the kinds of AI the working level allows. Installed system: `zenos-aiguard` (root) also enforces it in the packet filter. `zenos-keyd` records the highest level unsealed on the PC (`/run/zenos/exposed.json`) and, from L3, waits for the guard to confirm its rules before it hands out the plaintext. For every AI service the administrator listed (`/etc/zenos/ai.json`: external, government or ministry) or the office apps were pointed at (always counted as external), the guard asks `zenos-decide` and, wherever the flow decision says no, rejects the service's addresses in the `ZENOS_AI` chain for every program on the PC, not only the ZENOS apps. No answer from the decision is a block. Tested in a private network namespace with real rules and real connections (`tests/test_aiguard.py`): at L0-L2 all three kinds reachable, at L3 the external AI refused, at L4 and L5 only the ministry's AI; a service the apps were pointed at is learned and blocked; a removed hook is restored on the guard's next pass (2 s); an unreadable record counts as L5. | The exposure is per PC and falls only on a restart or an administrator reset (`sudo zenos_aiguard.py reset`), so after an L3 file an outside AI stays out of reach for the rest of the session. An AI reached at a name or address the guard was never told about is ordinary outbound traffic, left to the network sentinel and the open-time cut. Names are resolved by the guard: another program can get a different address for the same name, and an address shared with other sites behind a CDN is blocked for those sites too. Also tested on the 0.1.1 image in a virtual machine, live and after a disk install (Calamares, full-disk encryption, a new user given L4 by the administrator): L3 refused the external AI and, once the office server had been pointed at it, api.openai.com; L4 left only the ministry's AI; with the guard stopped or restarting, an L3 file stayed closed ("Try again in a moment"). |

## If someone takes root on the PC

Kernel holes that give root, sometimes from the network and without signing in, keep being found: CVE-2026-98432
in Multipath TCP was reported by Anthropic on 27 October 2026 and fixed in Debian's kernel 6.12.113-1, which the 0.1.1
image already carries. ZENOS is designed on the assumption that the kernel can have such a hole on any given day.

| | Today (0.1.2) | With the key service (in the repository, not in a release yet) |
|---|---|---|
| Taken with root | The level keys (root-owned files), so every file sealed on that PC. The guard, the AI guard and the audit shipping can be stopped. Records written in the seconds before they are shipped can be changed, and the signed status can be faked with the PC's audit key. | Files not yet sealed again through the key service (`zenos_keyd.py --reseal`, then `--drop-local-keys` destroys the keys left on the PC). The use of the PC's identity: root can ask the key service for files that a user assigned to this PC on the service is cleared for, as the service holds the clearance, a limited number per minute per user and per PC, each one recorded on the service at once. On a PC with a TPM the identity key is made inside it and cannot be copied: root has to ask from that PC, while it is reporting, and a PC started with another Secure Boot state cannot use the key at all. Root can also fake the PC's signed status (services running, no stop). From the presence level up (off until the confirmation pages ship), only files the user confirms on their own phone, on a page the key service serves, reached from a link sent to the person's ZENOS Messages and never through the PC. |
| Not taken, or still seen from outside | Files sealed on other PCs (the keys are per PC). Ledger records already shipped: the audit nodes refuse a rewritten history. A PC that stops shipping is reported silent after 90 seconds. A stopped guard, key agent, AI guard, network sentinel or firewall, and a kernel fix installed but not yet running, are reported by the audit nodes from the PC's signed status, every 10 seconds, for as long as the shipping runs. | Keys of files sealed with the key service: none is stored on the PC. Users not assigned to this PC on the service. A PC whose audit shipping stopped gets no key after 90 seconds (a PC that reports a stopped service or a stop gets none either, but root can fake that report). Each release is in the service's own chained log; a release the PC's shipped ledger does not record is reported (`--reconcile`). Claiming another level or another file id gives a key that does not fit. A silent PC, a refused key from an unhealthy or stopped PC and a release the PC did not record reach the officers through ZENOS Messages within seconds of being noticed. |
| Fewer ways in | New inbound TCP is dropped before it reaches a listening program (`ZENOS_IN`). Multipath TCP, io_uring and unprivileged BPF are off; kernel addresses and the kernel log are hidden from users; modules for unused network protocols, old file systems and FireWire are never loaded (`/usr/lib/sysctl.d/60-zenos-hardening.conf`, `/usr/lib/modprobe.d/zenos-blacklist.conf`). The kernel starts in lockdown "integrity" mode: even root cannot load an unsigned module, write to kernel memory or replace the running kernel (`/etc/default/grub.d/zenos-hardening.cfg`; tested in a VM: the network sentinel's eBPF sensor still detected an outgoing send to an unknown address, stopped the program and blocked the address). A waiting kernel fix restarts the PC when nobody is signed in (`zenos-restartwindow`, policy `kernel_restart`). In the repository: the key agent, which reads what users send it as root, runs with no capabilities, no home folders and no writes outside its own state; the AI guard keeps only the network capabilities and the audit shipping only the right to read the ledgers. A flaw in one of them no longer gives the rest of the system. These limits do not hold against a kernel hole. |

Next, in this order (0.2):

1. Keys off the PC: done in the repository (`zenos_keysvc.py`, [docs/KEY_SERVICE.md](KEY_SERVICE.md), proved in
   `KeyService.lean`): the service refuses a silent or unhealthy PC, keeps its own record of every release and
   compares it with the PC's; old files can be sealed again through it and the keys on the PC destroyed.
2. The identity key in the TPM: done in the repository (`zident.py`, `zenos-identity.service`): made inside the TPM
   on first start when the PC has one, bound to PCR 7. Officers' keys on FIDO2 tokens are still to come.
3. Alerts to the officers through ZENOS Messages: done in the repository (`znotify.py`).
4. Confirmation on the phone, on the key service's own page: the service side is done and tested; the pages wait for
   their design to be checked. Until they ship, the presence level stays off by default.
5. The root services confined (systemd): key agent, AI guard and audit shipping done in the repository; the guard
   and the network sentinel next, then mandatory access control (SELinux MLS).

ZENOS does not use kernel livepatching; a fix takes effect at the next restart, and the restart window and the audit
nodes make sure a waiting fix is seen and applied.

## If the update path is taken over

On 29 October 2026 Kaspersky reported NetamLoader (https://securelist.com/netamloader/121676/): on a Windows 10 build
used by government entities in Asia, a CAB archive in the Windows update folder held mostly genuine, signed
components of a patch tool, plus one crafted configuration file and one data file; a genuine signed program loaded
them. Its controller posed as an AI service (openaigpt4v.com). A signature check on the program does not see this.
ZENOS updates itself every day, so its update path is exactly such an entrance.

| | Today (0.1.2) | In the repository, not in a release yet |
|---|---|---|
| What lets a package in | apt's signature check on the repositories (Debian, NodeSource, ZENOS). Whoever holds a repository's signing key, or takes over its server, can ship any package to every PC. | Also the release ledger (`zenos_pkgcheck.py`, apt's pre-install check; proved in `Supply.lean`): the exact file (SHA-256) must be in a record that more than half of the audit nodes configured on the PC hold identically, signed by at least two release officers enrolled on the PC, not revoked (an officer-signed revocation counts wherever it is found), and released to this PC's ring. dpkg is then given root-only copies of the files, checked again by their SHA-256 (`zenos-dpkg`), so a file swapped in the download folder after the check is never what dpkg reads. One audit node, one officer's key, the publisher, or the repository server alone does not let a package in. With `"enforce"`, nothing installs while the audit nodes cannot be reached, and one refused package stops that whole apt run. Debian and NodeSource packages are recorded the same way after their file is checked against the signed index (`zenos_release.py manifest --apt-check`). Off unless `/etc/zenos/supply.json` turns it on (`"warn"` or `"enforce"`); every package installed is recorded in the PC's ledger either way. |
| A file that does not belong in the update folder | Not looked at. | `zenos-supplywatch` checks every file that appears in apt's download folder at once: a package file must be in the ledger, anything else does not belong there; either is quarantined and reported to the audit nodes, which alert the officers. |
| A genuine program fed a changed file | Not looked at. | `zenos-integrity` (hourly): every file of a package whose record the PC accepted, byte for byte, configuration files included (a changed configuration file is reported for review, a changed program as an alert); every other package against dpkg's own sums; and anything no package owns among the paths that make a genuine program load something else: `/etc/ld.so.preload`, `LD_PRELOAD` and similar variables in environment files and systemd settings, Python `.pth` and `sitecustomize` files, systemd drop-ins, apt hooks, `ld.so.conf.d`, `npmrc`. |
| Where system services may connect | Any address; large sends to unknown addresses are cut by the network sentinel. | Root and service accounts may reach only named destinations (the update mirrors, the audit nodes, the key service, the DNS servers; `/etc/zenos/egress-system.json`). Anything else is recorded (`"monitor"`, the default) or its address cut at the first byte (`"enforce"`; proved: `sysegress_cut_only_unlisted`). The mirrors in apt's sources, NetworkManager's connectivity check and the upstream DNS servers are added automatically. The sensor sees IPv4 TCP only (not IPv6, UDP or QUIC). |
| Reproducing a build | Not checked. | `packaging/repro-check.sh` builds the package twice in separate places and compares the bytes; `zenos_release.py manifest --rebuilt` refuses to describe a file that a listed rebuild does not match. A build record (`.buildinfo.json`) is written next to the package. |
| Rollout | Every PC at once. | Each record says when each ring of PCs may install it (`--rings 0=0,1=+1d,2=+3d`); a revocation signed by enough officers stops it everywhere. |

Not done yet: the ISO is not reproducible; the officers' release keys are files (hardware keys next); the audit
nodes that hold the release ledger and the mirror for Debian and NodeSource are not running for the public
preview, so the check stays off by default; kernel IMA/EVM: Debian's kernel has IMA, IMA appraisal and EVM built in,
and in a VM with lockdown "integrity" and `ima_policy=tcb` the kernel measured every program and library it ran
(31 October 2026). Appraisal (refusing a file whose hash is not signed) needs signatures on the files themselves
(`security.ima`), which Debian's packages do not carry; signing ZENOS's own files and appraising them is the next
step, and the measurement list is to be sent to the audit nodes with a TPM quote.

## Known weaknesses in dependencies

- `xlsx` (SheetJS) is no longer published on npm; the npm copy (0.18.5) has known vulnerabilities (prototype
  pollution CVE-2023-30533, ReDoS CVE-2024-22363). ZENOS uses 0.20.3 from SheetJS's own CDN, pinned in
  `package-lock.json` by its sha512 integrity, so a changed tarball fails the build. The CDN is a single source:
  watch it for new releases, since `npm audit` cannot see it.
- `mammoth` (Documents, .docx import) pulls `argparse` 1.x → `sprintf-js`, flagged moderate (GHSA-hp3w-g68c-fv3c).
  Both belong to mammoth's command-line tool and are not reached from the browser bundle; the only "fix" npm
  offers is a downgrade to a 2016 mammoth, so it is left until mammoth updates.

Every claim in the README must be backed by this table. A row moves to "real" only together with a test that
demonstrates it.
